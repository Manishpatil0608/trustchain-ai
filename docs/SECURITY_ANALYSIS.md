# Security Analysis

## Authentication vs Authorization Separation
TrustChain-AI strictly enforces the separation of **cryptographic identity** from **behavioral trustworthiness**. 
- A valid `did:key` Verifiable Credential acts solely as an authentication layer, proving the agent was cryptographically granted a capability. 
- The Adaptive Authorization middleware intercepts the request post-authentication to evaluate behavioral trust.
This resolves the critical security flaw where compromised agents historically retained access simply because their keys had not expired.

## Administrative Revocation
The engine provides a `REVOKED` state manually triggered via administrative endpoints (`POST /api/v1/trust/revoke/{did}`). This explicitly burns the agent, enforcing a terminal state that bypasses the mathematical decay model and actively ignores any subsequent "good" telemetry.

## Replay Considerations
The current framework mitigates simple replay attacks on telemetry by requiring unique UUID `task_id` signatures for every metric ingestion. However, because telemetry is not currently signed by a hardware enclave or attested trusted execution environment (TEE), advanced injection attacks from compromised API gateways remain possible.

## Current Vulnerabilities
- **Prototype Centralization**: The SQLite trust repository is a single point of failure.
- **Unauthenticated Admin Endpoints**: For demonstration purposes, the `/revoke` endpoint currently lacks rigorous administrative authentication mechanisms.
- **Untrusted Attestation**: The system lacks cryptographic proofs of the telemetry generated by the API execution layer.

This implementation is an academic validation of a temporal trust math model. **It is not fully decentralized, not fully secure, and not enterprise-ready.**
